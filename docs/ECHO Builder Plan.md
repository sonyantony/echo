# EY ECHO Builder: Version 1 Build Plan

Version 1 is a demo prototype. This plan favours simplicity over production hardening, while keeping the seams (auth, Git, CI, secrets, database) that later versions will need.

Sources: `Initial Requirements.md` (including "Version 1 decisions") and the project's recorded decisions as of 2026-10-14.

---

## 1. Technology stack

| Area | Choice | Why |
|---|---|---|
| Flow editor (drag and drop) | **Kaoto** (Apache 2.0), embedded via the `@kaoto/kaoto` npm package | Mature visual editor for Camel YAML DSL; no need to build our own canvas |
| Data mapping | **Kaoto DataMapper** (JSON via JSON Schema). Fallback: **JSONata** (`camel-jsonata`) or Camel `simple` expressions edited in Kaoto | Visual field mapping without a custom mapper. JSON support is verified in Milestone 1 |
| Builder UI shell | **React 18 + TypeScript**, **Vite**, **PatternFly 5** (the UI kit Kaoto already uses), **React Router**, **TanStack Query** | Thin shell around Kaoto: login, flow list, publish button. PatternFly keeps the look consistent with Kaoto |
| Builder backend | **Java 21 + Spring Boot 3.x** (Web, Security, Data JPA, Validation, Actuator) | Team's strongest stack; well suited to Claude Code generation |
| Login | **Spring Security** form/session login, users in `application.yaml` (BCrypt hashes) via an `InMemoryUserDetailsManager` built from config | Swappable later for OIDC/SAML SSO by changing the security config, not the app |
| Builder database | **H2 in file mode** (embedded), **Flyway** migrations, JPA | Zero ops for the demo; Flyway keeps a clean path to PostgreSQL |
| Git publishing | **JGit** (Eclipse JGit) over HTTPS with a token or username/password | Works with any Git server (GitHub, GitLab, Bitbucket, Azure Repos), so no provider lock-in |
| YAML validation | **Camel YAML DSL JSON Schema** (from `camel-yaml-dsl`) checked with `networknt json-schema-validator`, plus a Camel route-load check | Catches broken flows before they reach Git |
| Secrets | `application.yaml` / environment variables (Spring property binding) | V1 decision; Spring's property sources let a vault be plugged in later |
| Runtime | **Apache Camel 4.x on Spring Boot**, produced by **Camel JBang `camel export --runtime=spring-boot`**; by default all flows in one app and image (`bundle`), or one per flow (`per-flow`) | V1 decision: exported Camel apps, not the Camel K operator. Build mode: decision 0009 |
| Messaging | HTTP + JSON only: `platform-http` (inbound), `http` component (outbound), Jackson | V1 scope |
| CI (sample) | **Jenkinsfile** in the flow repo: export, `mvn package`, Docker build, push to a registry (e.g. JFrog Artifactory) | One working example; any CI can run the same steps |
| Container image | **Jib** (Maven plugin) or a plain Dockerfile | Jib needs no Docker daemon in CI, which suits more buyer pipelines |
| Packaging the Builder | **One Docker image** (Spring Boot serves the built React app) + **docker-compose.yml** | Simplest self-hosted install for about 10 users |
| Testing | JUnit 5, Spring Boot Test, Testcontainers-free Git tests (local bare repo via JGit), `camel-test-spring-junit5`; Vitest + React Testing Library; **Playwright** for end-to-end | Claude Code can verify its own changes at every milestone |
| Repo tooling | Maven (backend, runtime template), pnpm (UI), `CLAUDE.md` at repo root | Consistent context for every Claude Code session |

**Vendor-neutral rules:** no cloud SDKs, no provider-specific Git APIs, no hard-wired CI or IdP. Everything buyer-specific is configuration.

## 2. Architecture (Version 1)

```
Browser
  └─ React shell (login, flow list, publish)
       └─ Kaoto editor (canvas + DataMapper), edits Camel YAML in memory
            │  REST/JSON (session cookie)
            ▼
Spring Boot Builder backend  ── H2 (file) : users' drafts, flow metadata, publish history
            │  JGit (HTTPS)
            ▼
Buyer's Git repo (one repo, one folder per flow, fixed branch)
            │  webhook / poll
            ▼
Buyer's CI (sample Jenkinsfile): camel export → mvn package → image (all flows, or one per flow) → registry (e.g. JFrog)
            ▼
Buyer runs the image wherever they like (EY ECHO's responsibility ends here)
```

### Flow repository layout

```
flows/
  <flow-name>/
    <flow-name>.camel.yaml      # route(s) generated by Kaoto
    mappings/*.xsl              # DataMapper output, if used
    schemas/*.json              # JSON Schemas used by DataMapper, if used
    application.properties      # non-secret flow settings (ports, downstream URLs)
    echo-flow.json              # EY ECHO metadata: name, description, version, author
Jenkinsfile                     # sample pipeline (builds changed flows)
```

### Builder data model (H2)

- `flow`: id, name (unique, folder-safe), description, status (DRAFT / PUBLISHED), created/updated by and at.
- `flow_file`: flow id, path, content (YAML, XSL, schema files), so drafts survive between sessions.
- `publish_event`: flow id, commit SHA, branch, user, timestamp, message.

Drafts live in H2; Git holds only published flows. Users come from `application.yaml`, so there is no user table in V1.

### Backend API (sketch)

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET/POST /api/flows`, `GET/PUT/DELETE /api/flows/{id}`
- `GET/PUT /api/flows/{id}/files/{path}`
- `POST /api/flows/{id}/validate`
- `POST /api/flows/{id}/publish` (validate, write files, commit, push; returns the commit SHA)
- `GET /api/flows/{id}/history`

## 3. Key risks, checked first

1. **Embedding Kaoto in our own React app.** Kaoto is published to npm and is already hosted inside other shells (VS Code, Kaoto web). The exact embedding API must be confirmed against the current Kaoto release. Fallback: host the Kaoto web build in an iframe and exchange YAML with the shell via `postMessage`.
2. **DataMapper with JSON.** Recent Kaoto versions support JSON documents in the DataMapper (driven by JSON Schema; the mapping runs as XSLT 3 via `camel-xslt-saxon`). Confirm that an HTTP JSON request can be mapped to a different JSON downstream request and back, and that the exported Spring Boot app runs it. Fallback: JSONata (`camel-jsonata`) or `simple` expressions, edited as step properties in Kaoto.
3. **Camel version alignment.** Kaoto's bundled Camel catalog, Camel JBang and the runtime must use the same Camel 4.x line. Pin one version in one place.

## 4. Milestones

Each milestone is small enough for a few Claude Code sessions, ends with something runnable, and has an explicit "done when" check. Milestones 1 to 3 can start in parallel.

### M0. Repository skeleton
- Monorepo on the `Version1` branch: `builder-backend/` (Maven), `builder-ui/` (Vite + pnpm), `runtime-template/`, `pipeline/`, `docs/`.
- `CLAUDE.md` with build/test commands, pinned versions (Java, Camel, Kaoto, Node), and coding conventions.
- A simple CI workflow that builds and tests both modules on each push.
- **Done when:** `mvn verify` and `pnpm test` pass from a clean checkout.

### M1. Spike: Kaoto embed and JSON DataMapper (go/no-go)
- Minimal React page that renders Kaoto, loads a YAML string and reads back the edited YAML.
- Build one flow: `platform-http` POST `/orders` receives JSON, DataMapper maps selected fields to a different JSON shape, `http` calls a mock downstream, response is mapped back.
- Run that flow with `camel run` (JBang), then `camel export --runtime=spring-boot` and `mvn spring-boot:run`.
- **Done when:** a `curl` against the exported app returns the mapped response, or the fallback (iframe and/or JSONata) is chosen and recorded in `docs/decisions/`.

### M2. Backend skeleton and login
- Spring Boot app with Spring Security session login; users and BCrypt passwords read from `application.yaml` (`echo.security.users[]`).
- Security config behind one `AuthenticationConfig` class so OIDC/SAML can replace it later.
- `GET /api/auth/me`, CSRF protection, Actuator health.
- **Done when:** tests prove a configured user can log in, a wrong password fails, and `/api/**` returns 401 when logged out.

### M3. UI shell and login screen
- React app with PatternFly: login page, top bar (user, logout), empty flow list page.
- Vite dev proxy to the backend; production build copied into the backend jar's static resources.
- **Done when:** Playwright test logs in and sees the flow list.

### M4. Flow drafts (CRUD)
- H2 file database with Flyway; `flow`, `flow_file` tables; flow CRUD API.
- Flow names validated as folder-safe and unique.
- UI: create, rename, delete, open a flow.
- **Done when:** API and UI tests cover create/list/update/delete, and data survives a backend restart.

### M5. Editor integration
- Open a flow in the embedded Kaoto editor; save the YAML (and any DataMapper XSL/schema files) back to the draft.
- Unsaved-changes warning; a "new flow" template with `platform-http` already in place.
- **Done when:** Playwright test creates a flow, adds a step on the canvas, saves, reloads and sees the step.

### M6. Validation
- `POST /api/flows/{id}/validate`: schema-check the YAML, then load it into a throwaway Camel context (no start) to catch unknown components or bad expressions. Enforce V1 scope: only HTTP/JSON components allowed.
- Show errors in the UI next to the publish button.
- **Done when:** unit tests cover a valid flow, malformed YAML, and a disallowed component.

### M7. Publish to Git
- `GitPublisher` interface with a JGit implementation: clone/pull into a local working copy, write `flows/<name>/…`, commit with the user as author, push to the configured branch. Serialize publishes with a lock (fine for ~10 users).
- Config in `application.yaml`: repo URL, branch, credentials, committer identity.
- Publish history stored in `publish_event` and shown in the UI.
- **Done when:** an integration test publishes to a local bare repo and asserts the commit and file contents; a manual test pushes to a real GitHub repo.

### M8. Sample pipeline and runtime template
- `runtime-template/`: settings the export needs (Camel version, Spring Boot version, Actuator health, JSON logging), so every flow image is built the same way.
- `pipeline/Jenkinsfile`: detect changed `flows/*` folders, run `camel export --runtime=spring-boot`, `mvn package`, build the image with Jib, push to a registry from parameters (`REGISTRY_URL`, credentials ID). No environment promotion; that stays with the buyer. Since 2026-10-21 a `BUILD_MODE` parameter builds all flows into one image (`bundle`, the default) or one image per changed flow (`per-flow`); see `docs/decisions/0009-bundle-flows-in-one-image.md`.
- A shell script with the same steps, for buyers without Jenkins.
- **Done when:** running the script locally on the M1 sample flow produces an image that answers the `curl` test from `docker run`.

### M9. Builder packaging
- Multi-stage Dockerfile: build UI, build backend, one runtime image (Java 21 JRE).
- `docker-compose.yml` with a volume for H2 data and the Git working copy, and `application.yaml` mounted from the host.
- **Done when:** `docker compose up` on a clean machine gives a working Builder at `http://localhost:8080`.

### M10. End-to-end demo
- Scripted demo: log in, create the "orders" flow with DataMapper, validate, publish, pipeline builds the image, run it, `curl` it.
- Playwright test for the Builder part; README walkthrough for the rest.
- **Done when:** the full demo runs from the README without manual fixes.

## 4a. Testing plan

Testing is automated from M0 onwards so Claude Code can check its own work. Every PR into `Version1` must pass the fast suites; the slower suites run on each merge.

| Level | What it covers | Tools | When it runs |
|---|---|---|---|
| Backend unit | Services, validation rules, flow-name rules, config binding, `GitPublisher` logic | JUnit 5, AssertJ, Mockito | Every commit and PR |
| Backend integration | REST API with real H2 and Flyway, security (login, 401, CSRF), publish to a local bare Git repo created with JGit in a temp folder | Spring Boot Test, MockMvc | Every PR |
| Flow validation | Sample flows (valid, malformed YAML, disallowed component, bad expression) through the validate endpoint | JUnit 5 with fixture files in `src/test/resources/flows/` | Every PR |
| Route behaviour | The sample flows actually run: HTTP request in, mapped JSON sent downstream (mocked), mapped response back. Covers DataMapper/XSLT or JSONata output | `camel-test-spring-junit5`, WireMock for downstream services | Every PR |
| UI unit | Shell components: login form, flow list, publish button states, error display | Vitest, React Testing Library | Every PR |
| End to end (Builder) | Log in, create a flow, edit on the Kaoto canvas, save, reload, validate, publish; checks the commit in a test Git repo | Playwright against the Builder started with a test `application.yaml` | Every merge to `Version1` |
| Pipeline and image | Run the export/build script on the sample flow, start the image, `curl` it, check the mapped response and health endpoint | Shell script + Docker in CI | Every merge that touches `pipeline/` or `runtime-template/` |
| Packaging | `docker compose up` from a clean state, Builder health check passes, login works | Shell smoke test | Before each demo build |
| Manual demo check | The M10 walkthrough against a real Git host and registry | README checklist | Before each demo |

Rules:

- **Golden flows.** A small set of sample flows (at least the "orders" HTTP-to-HTTP mapping flow) is kept in the repo and used by the validation, route, pipeline and end-to-end tests, so every layer is tested against the same input.
- **No external services in automated tests.** Git is a local bare repo, downstream HTTP is WireMock, the registry is skipped or local. Tests run offline and repeatably.
- **Each milestone's "done when" check becomes an automated test** in the suite above and stays there as a regression test.
- **Version pinning is tested.** A test checks that the Camel version in `runtime-template/` matches the one Kaoto's catalog and Camel JBang use.
- **Coverage target:** no hard percentage for the demo; every API endpoint and every validation rule has at least one passing and one failing test.
- **Not in V1:** load testing (about 10 users), security penetration testing, and cross-browser testing beyond Chromium. These come before any production use.

## 6. Ways of working with Claude Code

- One milestone per branch/PR into `Version1`, each with its own tests; ask Claude Code to run the tests before every commit.
- Keep `CLAUDE.md` current: pinned versions, commands, and the decisions from M1.
- Keep Kaoto unmodified; EY ECHO code wraps it, so Kaoto upgrades stay easy.
- Record each significant choice as a short decision note in `docs/decisions/`.

## 7. Out of scope for Version 1 (kept possible by the design)

- SSO / external IdP (swap `AuthenticationConfig`).
- External secret stores (Spring property sources).
- PostgreSQL (Flyway migrations already in place).
- Pull-request-based publishing and choosing the target repo (V2; `GitPublisher` interface).
- OpenAPI schema editor, Swagger UI on the runtime, request validation (V2).
- Protocols other than HTTP and formats other than JSON.
