Typical Steps of a Flow’s Development

a

Create a user story with sample northside requests and responses (defines the request and response payloads, plus query parameters)

b

Identify the downstream calls to make (one or many)

c (Optional)

Check whether the downstream calls can run in parallel to save execution time, or whether they depend on each other

d

Map data from the northside request to each downstream call

e

Map data from each downstream call to the final response

f. These steps are not limited to HTTP-based REST calls

ECHO

3

Every flow follows the same steps. Start with a user story that has sample northside requests and responses, decide which downstream calls are needed and whether they can run in parallel, then map the data in both directions. The same pattern isn’t limited to HTTP REST calls.

Technical Details: The DevOps Pipeline

ECHO

6

A designer builds the flow in the browser and the Builder publishes it to Git. The pipeline picks it up, builds one image and pushes it to JFrog. It then pulls that same image into dev1, test4 and production, and at each step pulls that environment's settings and secrets from the configuration repository. The image itself holds no environment values.

ECHO

7

Request Routing Using Ingress

Inside the cluster the Ingress acts like a switch. Each request is sent by its path: the ECHO flows each have their own path and one to three pods, and everything else still goes to the legacy application. ECHO only adds rules for its own paths, so the legacy code keeps working unchanged next to it.

The ECHO platform has five parts:

Can be deployed on standalone servers, but ECHO includes features designed for Kubernetes

Can run side by side with legacy deployments, using Kubernetes Ingress routing

Can be deployed in bundle mode (all flows in one pod) or per-flow mode (each flow in its own pod)

ECHO

8

Five parts. The Builder, a browser front end and a Java back end, is where flows are designed and isn’t part of the daily build. The pipeline scripts, the Kubernetes Ingress files and the Runtime images are what go to production. Ingress routing means ECHO flows can sit alongside existing legacy services.

9

Everything is built on well-known open-source parts: React, PatternFly, Kaoto and Apicurio in the Builder, Apache Camel and Spring Boot at runtime. Because every flow is plain-text Camel YAML, it can be reviewed, diffed and versioned like any other code.
